# Improving Deckl with real results

## Capture a failure before rewriting instructions

Keep the starting project, exact task prompt, assets, host/model, installed skill version, and other active design instructions. Retain before/after screenshots at identical viewports and interaction recordings when motion matters. Identify which quality got worse and where. Never attribute a result to Deckl alone if multiple conflicting design skills were loaded.

## Compare under the same conditions

Use disposable copies with no production credentials. Compare no-skill baseline, previous Deckl, and the candidate with the same model, brief, assets, and tools. Repeat across an expressive portfolio, a colorful cultural page, an existing strong design, and a task-heavy product surface. Repeat representative cases to avoid selecting one lucky output.

Review unlabelled results for brand identity, hierarchy, type, imagery, interaction, mobile behavior, and task completion. Record preferred/tied/worse and a reason. Keep failures as well as successes. Track time and tool cost when available.

## Evidence record

For each case record: starting revision; candidate skill revision; host/model; prompt; active skills; before/after artifact paths; changed behavior; functional checks; reviewer findings; known gaps. Use project-specific performance and accessibility expectations.

## Publication

Publish examples only after running the cases and checking asset permissions. Include the prompt, setup, versions, and limitations so someone else can reproduce them. This file is a protocol, not evidence that a benchmark passed. Current installer checks do not establish visual superiority over another skill or model.
